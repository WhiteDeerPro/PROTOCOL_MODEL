# 教材写作约定

本文件约束教材正文的讲述方式。架构文档重在准确记录工程合同；教材还需要安排认知顺序，让首次接触
项目的读者可以通过场景、图和 trace 建立直觉。

## 一节内容的基本顺序

正文优先采用以下顺序：

1. 给出一个具体场景；
2. 用一句日常中文说明本节要解决的问题；
3. 给出精确定义，并说明状态由谁保存；
4. 展示输入、输出和最小生命周期；
5. 解释设计理由和相邻层的边界；
6. 给出源码名称、可执行 witness 和练习。

章节可以按内容删减步骤，但概念及其理由应先于 API 清单和当前支持矩阵。

## 正面定义与对比

段落首句优先直接说明对象承担的工作，例如：

> Pattern 提取多种协议共有的事务关系，例如请求—完成配对、beat 计数和 FIFO 汇合。

“A 不是……而是……”容易形成连续的辩论语气，也会要求读者先理解 A。正文只在误解已经普遍存在、
两个概念处于同一比较维度时使用对比。其他对比放入“常见混淆”侧栏或边界表。

推荐改写：

| 辩论式句子 | 教材式说明 |
|---|---|
| Pattern 不是协议名称，而是可复用关系 | Pattern 保存可复用的事务关系；InterfaceProtocol 将这些关系与 channel、role 和 schema 组合成接口合同。 |
| Atomic 不表示整个事务原子发生 | AtomicFrame 的原子范围覆盖一次 lowering 输入；事务原子性由对应语义规则另行声明。 |
| Bridge 不是 A 到 B 的 callback | Bridge 先闭合两端能力和转换政策，再沿 request 与 completion 两个方向执行转译。 |

## 专用词汇的解释

术语第一次出现时使用“英文名（中文问题描述）”，随后保持一个稳定名称。例如：

> `InterfaceProtocol（完整接口合同）`描述两个端点在一条逻辑接口上可以交换的消息、方向和事务关系。

重要术语使用概念卡片，卡片包含：

- 场景：读者在什么问题中会遇到它；
- 直觉：一句白话说明；
- 定义：工程中的准确边界；
- 所有者：静态声明或运行状态存放在哪里；
- 生命周期：何时创建、更新和结束；
- 例子：最小 trace 或图；
- 边界：最容易混淆的相邻对象。

类比之后补充适用边界。每节控制新术语数量，并让新术语在同一节内参与一个真实例子。

## 论断的来源标签

教材用下面四类标签帮助读者判断结论的稳定程度：

- **协议要求**：来自协议规范，需要给出章节或条款来源；
- **架构选择**：本工程采用的建模边界，并说明它保护的性质；
- **实现状态**：绑定具体 release 的已有能力；
- **工程取舍**：由性能、复杂度或调试成本推动的选择，并给出重新评估条件。

## 图、代码和练习

- 一张图承担一个主要解释任务；总览图提供导航，细节图说明生命周期或所有权。
- 代码片段围绕可运行 witness 截取，正文先说明输入与预期结果。
- API、包路径和支持矩阵放在伴读框或附录，避免打断概念主线。
- 每章至少安排一题“规则属于哪一层”、一题“状态由谁保存”或一题“补全生命周期”。
- 当前未实现的内容集中记录在版本附录和工程依赖表中。

## 从工程文档取材

取材时重写叙事顺序，保留可核对的定义、图源和 witness。状态页、roadmap、发布说明和宣传材料作为
事实来源使用，不直接拼入正文。教材引用一个工程概念时链接其 canonical 架构文档，避免形成第二套设计
合同。
