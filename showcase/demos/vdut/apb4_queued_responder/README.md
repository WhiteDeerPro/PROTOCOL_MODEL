# APB4 queued-responder VirtualDut demo

This demo executes one small system assembled from the current modeling
layers:

- a source `VirtualDut` boundary with an external, seeded random traffic
  controller;
- one APB4 `InterfaceProtocol` instance;
- an APB4 completer attachment bound to a finite queued address backend;
- a memory region reached when an explicit `DutAdvanceAction` services the
  queue.

Run it from any working directory:

```bash
python3 showcase/demos/vdut/apb4_queued_responder/run.py
```

The default publication is
`showcase/generated/vdut/apb4-queued-responder/`. The script stages the whole
publication before replacing that directory. It keeps the WaveJSON and DOT
sources beside the SVG views and records the seed, command, model version and
presentation boundary in `provenance.json`.

Use `--publish-root <directory>` when the generated evidence should live in a
scratch or another release tree; constructing or running a VirtualDut by
itself does not choose an output directory.

The WaveDrom view is an event/service-step projection. It shows generated APB4
canonical requests, explicit backend advances, FIFO state and completions. It
is not a fabricated PSEL/PENABLE waveform or an RTL/VCD capture. The separate
topology view shows where the scenario controller, two VirtualDut boundaries,
APB4 link, attachment, FIFO and address handler are connected.

The publication also includes `target-structure.svg`, generated by the common
VirtualDut projector rather than hand-maintained topology labels. It expands
the integration result into port, attachment, FIFO, delay/service controller
and AddressSpace components while leaving unknown external implementations
opaque.
